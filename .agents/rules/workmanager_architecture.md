# WorkManager システム全体設計・アーキテクチャ定義（AI開発ルール）

本ドキュメントは、WorkManager（和気センター WorkManager Pro）の全体像、各サブシステムの役割、データの流れ、および重要ビジネスロジックをまとめた開発指針です。GeminiおよびAIアシスタントは、本仕様とルールを前提として機能追加・リファクタリング・デバッグを行ってください。

---

## 1. システム全体概要 & 開発思想
WorkManagerは、現場でのデータ入力から進捗管理、スケジュール達成度確認、個人成績・生産性評価（ゲーミフィケーション）、AIフィードバックまでを包括する現場主導型の統合生産管理システムです。

### 核心設計思想
1. **現場ファースト・無停止運用（オフライン耐性）**:
   - 現場のデータ入力はサーバーダウンやネットワーク不調でも絶対に中断してはならない。ローカル（SQLite）に即時書き込み、バッチが非同期に中央DBへ同期する。
2. **リアルタイムな進捗共有と自動連動**:
   - 現場での実績入力が、中央DB・スケジュール実績・SV/作業員の端末画面へドミノ式に即座に反映される。
3. **現場作業員のモチベーション向上**:
   - NFCカードのワンタッチで個人ダッシュボードを起動。レーダーチャート、経験値・レベル、称号、AIフィードバック等で生産性とやりがいを可視化。

## 2. システム構成とデータフロー

```text
[現場作業端末 (PC1)]
  ├─ work_app.py (入力UI) ────(即時保存)────> SQLite (work_data.db)
  │                                                │
  └─ dashboard_workplace.py (進捗UI & 同期) <──────┘ (未同期データ読取)
             │
             ├──(非同期送信・保存)───> [中央DBサーバー: 192.168.10.101]
             └──(スケジュール自動連動)──> MariaDB: work_manager_db
                                           │
       ┌───────────────────────────────────┼───────────────────────────────────┐
       ▼                                   ▼                                   ▼
 [Windowsタブレット]               [Androidタブレット]                 [管理/開発PC]
  (キオスク: 13.3インチワイド)       (SV・管理者モード: 10インチ)        (Administrator)
  ・NFCタッチで個人実績              ・全体進捗/スケジュール管理          ・全機能/DB運用設定
  ・AIフィードバック/レベル          ・データ修正/削除/Excelインポート    ・データ分析/集計
```

### データ連携の詳細
1. **現場入力**: `work_app.py` からローカルの `work_data.db (SQLite)` に一時保存。
2. **同期＆スケジュール自動消化**: `dashboard_workplace.py` がSQLiteの未同期レコードを検知し、中央の MariaDB (`192.168.10.101`) へ同期。同時に後述の「前倒し消化ドミノ倒し」を実行。
3. **画面自動更新（トラッキング）**: 各種データが更新されると `data_update_tracker` の更新日時が更新され、Flutterアプリ群がこれを検知して自動リロードする。

## 3. 各アプリケーションの役割

| アプリ / モジュール | 主要技術・端末 | 利用対象 | 主な機能・役割 |
|---|---|---|---|
| **work_app.py** | Python (GUI/SQLite) | 現場作業員 | 清掃・整備データの高速入力。ネットワーク切断時も完全オフラインで入力可能。 |
| **dashboard_workplace.py** | Python (Flet/Matplotlib) | 現場作業員/リーダー | 現場全体のリアルタイム進捗画面。SQLiteからMariaDBへの自動同期およびスケジュール自動連動バッチ。 |
| **workmanager_flutter (キオスク)** | Flutter (Win: 13.3型ワイド) | 現場作業員 | NFCカードタッチによる「個人実績」「レーダーチャート」「レベル/称号」「AI分析」の瞬時全画面表示。 |

| **ai_analyzer.py / nfc_server.py** | Python | システム | 作業実績のAI自然言語フィードバック生成、NFCカードID読み取り・QR変換サーバー。 |

## 4. IPアドレスによるFlutterアプリの動作モード判定
`main.dart` 起動時、自身のローカルIPアドレスを判別して自動で画面モードを切り替えます。
- **`192.168.10.102`**: **キオスクモード (`AppMode.kiosk`)**（全画面・カードタッチ待機）
- **`192.168.10.103` / `150` / `151` / `152`**: **管理者モード (`AppMode.administrator`)**（全機能・DB運用設定利用可）
- **その他のIP**: **マネージャーモード (`AppMode.manager`)**（閲覧・スケジュール管理等）

## 5. 主要データベース定義 (MariaDB: `work_manager_db`)

| テーブル名 | 用途 | 重要なカラム・挙動 |
|---|---|---|
| **`unit_cleaning_logs`** | 清掃実績ログ | 実績メインテーブル（作業者ID, 機種名, メーカー名, air/clean/swap台数, 日時等）。 |
| **`t_schedules`** | 清掃スケジュール | 日程・機種ごとの予定と実績（`target_date`, `model_name`, `maker_name`, `plan_count`, `actual_count`）。 |
| **`t_model_schedules`** | 機種別作業累計 | 機種・メーカーごとの `air_count`, `clean_count`, `swap_count`, `total_count` の累計。 |
| **`m_models`** | 機種マスタ | 機種名、メーカー名、標準作業時間（目標時間）、機種特性などを管理。 |
| **`m_members`** | 作業員マスタ | 作業員ID、氏名、NFCタグID、所属などを管理。 |
| **`data_update_tracker`** | データ更新監視 | `id=1` の `last_updated` を監視。データ変更時に更新され、Flutter側が画面を自動同期。 |
| **`daily_targets`** | 日別目標設定 | 1日の目標清掃、エアー清掃、筐体交換の台数枠。 |

## 6. 特殊ビジネスロジック & 仕様ルール

### 🚨 スケジュール自動連動（前倒し消化ドミノ倒しロジック）
- **発動契機**: `dashboard_workplace.py` から中央 MariaDB へデータが同期された瞬間。
- **加算アルゴリズム**:
  1. 入力された清掃台数分を、該当機種・メーカーの `t_schedules` のうち**「一番古い未達成の予定（`actual_count < plan_count ORDER BY target_date ASC`）」**へ自動加算。
  2. その日の予定枠が100%達成された場合、あふれた台数は自動的に**次の日程の未達成枠へ繰り越して加算（ドミノ倒し消化）**。
  3. 全ての予定枠が100%達成済み（または未達成枠が存在しない）場合、**あふれた台数は切り捨て**、予定枠を無理に超過させない。
  4. 同時に `t_model_schedules`（エアー・清掃・交換の内訳）へも累積加算する。

### 📊 個人能力・生産性評価（レーダーチャート・ゲーミフィケーション）
`data_provider.dart` にて5軸のスコアを算出：
1. **スピード (Speed)**: `標準作業時間 / 実作業時間`（1.2倍で100%・A判定）
2. **品質 (Quality)**: エアー・清掃の完了比率（※筐体交換は不良率の概念がないため除外）
3. **技術 (Tech)**: 担当可能な機種バリエーション数（25機種でA判定）
4. **スタミナ (Stamina)**: 累積実稼働時間（2000時間でA判定）
5. **貢献度 (Contribution)**: 獲得ポイント（2000pt毎にレベルアップ、称号付与）

## 7. 画面・端末UI設計基準（13.3インチワイド / 10インチ最適化）
- **端末仕様とターゲット画面**:
  - **キオスク端末 (現場用)**: **Windowsタブレット 13.3インチ ワイド**（横向き / 概ね 1920×1080 Full HD, 16:9）
    - 現場作業員専用。13.3インチワイドの横長・大画面をフルに活かし、レーダーチャート、個人成績、AI分析、経験値・称号をスクロール不要の1画面（ダイナミックかつ高い視認性）で美しく収める。
  - **SV・管理者端末**: **Androidタブレット 10インチ**（横向き / 概ね 1280×800 ～ 1920×1200, 16:10 / 16:9）
    - 現場リーダー・管理者用。10インチ画面でスケジュール表、進捗円グラフ、データ編集テーブル等を操作性高くまとめる。
- **Flutter UI設計指針**:
  - **1画面完結レイアウト**: 各端末の画面サイズにおいて極力不要なスクロールを発生させず、主要情報が一目で収まるスケーリング・レイアウト設計を徹底する。
  - **タッチ操作の最適化**: 現場作業員の手袋装着時や指タップを考慮し、ボタンやカード等のタップターゲットは十分なサイズ・余白（マージン/パディング）を確保する。
  - **視認性の確保**: 現場の作業机やアームスタンド設置時など、一定の視認距離（50〜80cm程度）からでもはっきり読めるフォントサイズ・コントラストを保つ。
  - **レイアウト崩れ防止**: 解像度差やアスペクト比の違いによるはみ出し（`RenderFlex overflowed`）が絶対に起きないよう、`FittedBox`、`Expanded`、`Flexible`、レスポンシブなサイズ調整を適切に用いる。

## 8. 開発・実装における厳守事項
1. **画面サイズ要件の厳守**:
   - キオスク画面は **Windows 13.3インチワイド（1920x1080 / 16:9）**、管理者・SV画面は **10インチ横向き（1280x800〜1920x1200）** を前提として美しく収まるよう実装・確認すること。
2. **ロジックの破壊禁止**:
   - `t_schedules` の前倒しドミノ倒しロジック、および `dashboard_workplace` の同期処理の整合性を損なう変更を行わないこと。
3. **オフライン耐性の維持**:
   - `work_app.py` は常にローカルSQLiteファーストで動作させ、直接MariaDBへの依存を持たせないこと。
4. **現場UI/UXの配慮**:
   - 現場端末は照明の反射や暗所を考慮し、コントラスト・文字サイズ・カラーモード（ピュアホワイト / 反射低減ダーク）の切り替え設計を維持すること。
5. **環境依存・通信量の配慮**:
   - 現場・出先でのテザリング開発に対応できるよう、ローカル環境（`.venv`, Flutter precache, ローカルビルド）を優先活用すること。
